# Agent Note: dsh-kb milestone 5 — web governance workbench, flywheel dashboard, and read-only MCP server

Status: implemented

English | [中文](2026-08-19-dsh-kb-milestone-5-workbench-and-mcp.zh.md)

## Problem

Milestones 1–4 closed the model-facing loop: card write/read/search, knowledge-pack injection, the team library with the dual gate, freshness, heat telemetry, recap blind-spot detection, and the methodology skills. The human surface is still missing: the pending-review lists (freshness + recap blind spots) and the flywheel metrics reach only the model through tool results, so a person has no workbench, and the review queue has no notification channel. The reference pool is also not consumable from outside the harness: `packages/mcp/mcp-client` bridges external MCP servers in, but nothing serves the knowledge base out as an MCP server. Milestone 5 must fix the workbench scope, the notification channel, and the MCP exposure boundary first, then implement the minimal closed loop.

## Decision

**The workbench is a web settings section driven by one host Remote service.** The new package `@deepseek-ai/dsh-kb-web` (`packages/kb/kb-web`) exposes `ctx.kbWorkbench` (`KbWorkbenchService extends TypertRemoteService`, namespace `kbWorkbench`) with `@Remote` methods: `overview` (the merged pending-review list plus the flywheel metrics), `card` (one full card), and the lifecycle actions `promote` / `archive` / `revive` / `review`. The browser half is the new client plugin `@deepseek-ai/dsh-client-ui-kb-workbench` (`packages/client/ui-kb-workbench`), which registers the `settings.section` entry id `kb-workbench` (nav label 知识库) and renders the pending-review list, the card detail, the action buttons, and the flywheel dashboard. Every Remote method takes the session first (the `session` Typert lookup carries the session id on the wire); the host derives the workspace root from `session.header.cwd`. The workbench is an opt-in composition: a deployment mounts `@deepseek-ai/dsh-kb-core` + `@deepseek-ai/dsh-kb-web` + the client plugin through its own `cordis.yml`, and `examples/kb-web/cordis.yml` is the documented overlay. Shipped bundle defaults do not change: kb stays out of `packages/bundle/web-app` exactly as in milestones 1–4.

**Workbench actions are thin event-appending wrappers over the existing `ctx.kb` methods — no new state machine.** Each action performs the exact service call the corresponding tool performs — `ctx.kb.promote`, `archiveTeam`, `reviveTeam`, `reviewTeam` — and then appends the same `kb/*` session event the tool appends (`kb/promote` carrying the transition; a rejected `review` appends nothing, exactly like `kb_review`) to the workbench session's own log. The human's click is a session fact, reconstructable from the session log like a tool call, so the "model-visible ⟺ logged" invariant holds for the write side. Card content editing is deliberately not an action: kb has no edit operation with established event semantics, and inventing one for a single UI affordance would create a second mutation path; changing card content stays a model task through `kb_write` (new draft) plus the dual gate. The workbench's action set is exactly the lifecycle transitions the existing seam already supports.

**The pending-review list merges the two existing read surfaces, and the flywheel metrics are pure projections.** `overview` returns the freshness review (`kb.freshnessReview`), the unrecorded recap blind spots (`liveRecapLogSource` + `RecapCheckpoint` read + `detectBlindSpots` — detection without recording, so the workbench never advances the checkpoint and the tool/scheduler queue semantics are untouched), the heat ledger (`kb.heat`), and five flywheel metrics projected from those same surfaces: injection count (heat-ledger total), top-heat cards (the top three heat rows with titles), promotion count (a fold of `kb/promote` events over the recap log source), pending-review count (freshness overdue + expiring-soon), and unrecorded blind-spot count. No second event stream exists: every number derives from `kb/*` events or their persisted projections (heat ledger, recap checkpoint, card files).

**The notification channel is the workbench's pending-review list; IM is deferred.** The recap and freshness outputs already reach the model through the tool results and the scheduled job outputs; the workbench is the human-facing channel. IM push stays a documented limitation with a trigger condition (a real ops-channel requirement), recorded in the package READMEs.

**kb-mcp splits into inbound wiring and a new outbound read-only server.** The inbound middleware — connecting external MCP servers to dsh, or splitting events/logs/alerts per domain — is connector/config work over the existing `mcp-client` (the `examples/mcp-memory` pattern) and ships no new code. The outbound exposure — serving the reference pool to external MCP clients — is a minimal read-only MCP server: `@deepseek-ai/dsh-kb-mcp-server` (`packages/kb/kb-mcp-server`), stdio transport via the `@modelcontextprotocol/sdk` (already a workspace dependency of mcp-client), four read-only tools (`search_cards` / `read_card` / `freshness_review` / `heat`) calling `ctx.kb` methods, and a `bin` that boots a minimal composition (agent / system-prompt / tools / session / kb-core / server) and connects `StdioServerTransport`. No write tools: the write side stays inside the harness (tools and workbench) where `kb/*` events are logged. The server lives in the kb package group rather than a generic `packages/mcp/` seam because a generic MCP-server seam would have exactly one consumer — the "current owner and need" rule in `packages/AGENTS.md` — and the SDK already provides the machinery.

## Alternatives considered

**A generic MCP-server seam in `packages/mcp/`.** Rejected: one consumer (kb) does not justify a new capability seam, and the SDK's `McpServer` / `StdioServerTransport` is the maintained machinery. Extract a seam when a second server consumer exists.

**The workbench runs a recording recap scan on open.** Rejected: recording advances the checkpoint invisibly to the model, paging the blind-spot queue without distillation; read-only detection keeps the queue semantics with the tool and the scheduler, which are the only recording paths.

**The workbench ships in the web-app bundle.** Rejected: kb is an opt-in plugin family; adding kb-core to every web session would change the shipped product default (its tools and injection). The opt-in overlay matches the `examples/mcp-memory` and `examples/web-cordis` precedent.

**IM notification now.** Rejected: no ops-channel requirement exists yet; the workbench list is the human surface, and the deferral keeps a documented trigger condition.

**A card edit operation in the workbench.** Rejected: it would invent a new state mutation path and event semantics for one UI affordance. Editing stays with the model through `kb_write` (new draft) plus the dual gate, and lifecycle actions cover the human loop.

## Consequences

New packages: `packages/kb/kb-web` (host Remote service + event appends), `packages/kb/kb-mcp-server` (read-only MCP server + bin), and `packages/client/ui-kb-workbench` (browser half). `packages/api/remotes`' client assembly imports the kb-web remote contribution so the browser can reach the namespace; the workbench client plugin joins the assembled-jsdom boot list for browser snapshots, and the shipped web-app bundle is unchanged. The `packages/client/connection` fixture serves the `kbWorkbench/*` endpoints for the keyless snapshot lane, with the new fixture cases covered by a connection-package spec to keep per-file 100% coverage. `docs/subsystems/kb.md`, the kb-core README (the "Web workbench and MCP exposure are deferred" limitation is replaced by pointers to the new packages), the new package READMEs, and the generated catalogs update together. Gate additions: the assembled-jsdom browser snapshot (`apps/web/tests/kb-workbench.snapshot.ts`), Loader-composition tests for both host packages, and the MCP server's real-composition stdio test through the SDK client.
