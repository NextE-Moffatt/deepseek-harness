# Agent Note: dsh-kb 卡片 schema 演进——解析器即版本权威、增量式字段、索引重建

Status: implemented

[English](2026-08-19-dsh-kb-card-schema-versioning.md) | 中文

## Problem

知识卡片是 Markdown + YAML front matter，是个人库与团队库共用的一份用户可见格式。字段集会演进（团队库 L1–L4 层级与治理字段是已知候选），每次变更后所有存量卡片与 FTS5 索引都必须保持可读、可检索。里程碑 2 kickoff 的待决项 5 是版本化与迁移策略：字段增删如何落地而不破坏存量卡片、索引与未来的解析器。

## Decision

**卡片文件不携带 schema 版本字段；解析器就是版本权威。** 文件是合法卡片，当且仅当当前解析器接受它。版本字段会制造第二个权威，可能与解析器不一致；而手写 Markdown（设计的编辑模型）不应因版本头维护而失效。存储的 list 已经按文件报告解析失败而不是丢弃文件，所以不可解析的卡片始终可见，绝不静默跳过或自动重写。

**字段演进只做增量；未知键继续 loud fail。** 新字段以可选 front-matter 键随解析器同一变更落地；没有该键的存量卡片以字段缺失读取，`kb_write` 在适用时提供默认值（有效期 → `now + cardTtlDays` 是既有模式）。重命名、删除、改类型、或把既有键改为必填是破坏性变更，必须走显式的迁移 pass 重写卡片文件——pre-release 立场是正确的地基优先于兼容垫片，而旧解析器静默误读新文件正是 loud rejection 要防的失败模式。未知键拒绝保留：带未知键的卡片 loud fail，而不是在下一次写时被去掉该键重新序列化（那会静默丢弃用户放进去的数据）。

**索引演进 = schema bump + 既有的原地重建。** `kb/.kb-index.sqlite` 上的 FTS5 数据库持有 `KB_SEARCH_SCHEMA_VERSION`（当前 1）、`PRAGMA application_id` 与 `PRAGMA user_version`；打开的索引版本与当前不一致时 drop 并重建表，下一次 sync 从卡片文件重建内容。因此新增结构化过滤列 = 升版本常量，迁移就是既有的 drop-and-rebuild——FTS 内容是从卡片派生的数据，不存在独立的数据迁移。卡片 id（`{type}-YYYYMMDD-{seq}`）是稳定契约，永不迁移。

**团队库迁移是受治理的 rollout，不是自动重写。** 团队卡片跨 checkout 共享；破坏性解析器变更不能在任何 checkout 还读不懂其输出之前上线。迁移 pass（一个重写卡片文件的文档化脚本）与解析器变更同一次提交进团队仓库，变更的 rollout 说明写明顺序：先迁移仓库，再升级插件。kb 绝不因为解析器变了就原地重写卡片文件。

## Alternatives considered

**front matter 加 `schemaVersion` 字段 + upgrader 链。** 拒绝：字段与解析器两个权威可能不一致，手写卡片需要维护版本头，而且 session 日志的 upgrader 模式不适用——卡片文件是用户内容，不是机器持有的日志。

**自动重写带未知键的卡片。** 拒绝：不带未知键序列化会静默丢弃用户数据；loud fail 让写路径诚实，并迫使解析器变更与字段同时落地。

**版本化目录布局（如 `cards/v2/`）。** 拒绝：卡片 id 跨库与知识包是身份标识；目录迁移会打断每个 id 引用与晋升状态机，而没有任何迁移收益。

## Consequences

每次字段新增都是同一个变更：解析器、必要时索引 schema bump、文档一起落地；存量卡片保持可读，旧索引首次打开时自行重建。破坏性字段变更是一次协同 rollout（先迁移团队仓库，再升级解析器），而不是静默兼容垫片——代价是协调，收益是任何解析器都不会静默误读卡片。索引的版本不匹配原地重建路径已有测试覆盖，未来 schema bump 复用同一套被验证的机制。
